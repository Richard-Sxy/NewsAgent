Agent 之间一律通过「S3 Artifact 存内容 + PostgreSQL Checkpoint 存状态 + 只传 URI」间接交接。
编排权在 Temporal Workflow，Agent 只是被调用的无状态函数。

五个通道（复用口径）：
1. **进程 → FastGPT**：HTTP，`app/clients/fastgpt.py`(241)。OpenAI 兼容
   `POST /api/v1/chat/completions`，`httpx.AsyncClient`，timeout 120s/connect 10s。

   variables 只带 `mode` 和 `output_schema`。`_unwrap_json_code_fence` 只接受纯 JSON 或

## 用户追问：为何没有 Agent 通信 / 企业项目该怎么写（本轮）

用户疑问："是不是因为接了 FastGPT 才这样？企业项目的写作 Agent 应该有通信吧？怎么写？"

回答口径（复用）：
- **FastGPT 是诱因但不是根因**。FastGPT 确实自带完整工作流引擎
  （`FastGPT/packages/service/core/workflow/dispatch/` 下有 ai / dataset / tools / plugin /
  loop / parallelRun / interactive 节点），但本项目只用了"单 App 执行"这一种模式
  （`POST /api/v1/chat/completions`，一次输入换一次结构化输出），天然无状态单轮。
  根因是编排权放在 Temporal：只要要求长跑/可重放/可审计/人工审批，就必然走产物交接。
- **把编排搬进 FastGPT 内部工作流的代价**：业务规则变成不可 review、不可单测的 JSON 配置，
  且失去 Temporal 的重放、心跳、人工 Signal/Update 门、Checkpoint。不建议。
- **"通信"要分四种，别混为一谈**：① 数据交接（已有：Artifact+Checkpoint）② 工具调用
  （Agent 主动索取能力，**当前缺**）③ 反向请求（Agent 向编排器求助，**当前缺**）
  ④ Agent 间协商/辩论（生产基本不用，成本高、不确定、难审计）。
  现在写作 Agent 是"一次性开卷考试"，拿到输入包一次性吐结果，不能说"我再查点资料"。

给的方案（三层，**只做设计讲解，未写任何业务文件**，遵守不改代码约定）：
1. **受控工具循环**（最该先做）：在 Temporal Activity 内部跑有界 ReAct。
   新增 `AgentAction` / `AgentStep` Schema（action 与 final 二选一，model_validator 校验）；
   `TOOL_REGISTRY` 白名单；每轮 heartbeat + 单轮 timeout + 总 deadline + 轮数上限；
   工具只读、args 逐工具 Pydantic 校验、工具返回值按不可信数据包裹后回填；
   每轮落 `agent_runs`（round_no / tool / args / tokens）。超轮数上限转人工而非直接失败。
2. **反向请求**：`AgentRequest{kind: more_evidence|human_clarification|data_unavailable}`
   挂在输出 Schema 上，Workflow 读到 `outcome.requests` 再决定跑补充检索或转人工，
   比让 Agent 自己调工具更安全（决策权在 Workflow）。
3. **真 A2A**（Agent Card + 任务契约 + HTTP/gRPC + 幂等键）：只在 Agent 由不同团队部署、
   需独立演进时才值得。单人/单团队维护的写作系统引入 A2A 属过度设计。

落地顺序建议：1 → 2 → 3（3 先别碰）。

## 视频新闻入库可行性走查（tencent-news-crawler 知识库链路）

只读分析，未修改任何文件。用户诉求：视频新闻只需"分类聚合级"入库，不需要逐帧理解。

现状结论：**当前代码不支持视频新闻入库**，四处阻塞：
1. `crawler/topic_crawler.py:237` `if article_type == "4": continue`，发现层直接丢弃视频。
2. URL 形态不匹配：`topic_crawler.ARTICLE_PATH_PATTERN` 与 `tencent_sitemap.ARTICLE_URL_PATTERN`
   都只认 `^/rain/a/[A-Za-z0-9]+$`，视频页（/omn/、含 vid）会被 `normalize_article_url` 返回 None。
3. `TencentNewsCrawler._parse_content` 只抓 `<p>`，视频页正文为空 → `format_article_text` 产出
   "标题+URL+时间"空壳，向量化后成噪声，但仍会 `mark_success` 记为成功。
4. 数据模型无媒体类型概念：`NewsArticle` 无 media_type/video_url/duration；
   `news_ingest_records` 表无对应列；`create_news_collection` 的 metadata 也无，检索侧无法按类型过滤。

两个已实测确认的前置缺陷：
- `crawler/tencent_news.py:249` `_parse_article_id` 缺函数体 → `IndentationError`，模块无法 import
  （与 PROJECT_CONTEXT 第 9 节记录一致）。
- `NewsArticle` 的 dataclass 字段 `news_id: str | None = None` 与同名 `@property news_id` 冲突，
  即使修好缩进，`NewsArticle(...)` 也会抛 `AttributeError: property 'news_id' has no setter`。

关键架构事实：**本项目无本地向量化**。`rag/embedding.py` 是 1 行空文件，`rag/chunker.py` 未被
入库链路调用；向量化完全委托 FastGPT（`trainingType="chunk"` + `chunkSettingMode="auto"`）。
因此视频入库等价于"造一段够好的文本代理"，不需要多模态模型。

推荐方案（分级文本代理）：L0 纯元数据卡 / L1 页面可见文本（og:description 等，**默认推荐**）/
L2 ASR 转写（白名单开启）/ L3 抽帧 OCR（明确不做）。进阶建议：复用
`intelligence/event_clustering.py`（TF-IDF + 实体 + 数字相似度）先按事件聚类，再以"事件聚合文档"
入库，避免单条视频文本过薄，也直接满足分类聚合目标。

改造点已按文件+行号给出：tencent_news.py（修 news_id 冲突、加 media_type 等字段、
新增 _detect_media_type/_parse_video_meta）、news_ingest_service.py（format 分支 + 内容充分性闸门）、
fastgpt_client.py（metadata 增补）、ingest_repository.py（migrate 加列）、topic_crawler.py
（video 开关 + 不强拼 /rain/a/）、config.py（新增开关）。

关联发现：热点侧 `NewsMetricCalculator` 已有 article 20s / video 10s 的有效消费阈值区分，
说明业务模型里 video 是已知类型，只是入库侧缺失。

## 视频→摘要→入库：现成方案调研（含 FastGPT 能力盘点）

**FastGPT 自身能力盘点（读源码确认）**
- 知识库上传白名单**不含视频**：`documentFileType = '.txt, .docx, .csv, .xlsx, .pdf, .md, .html, .pptx'`
  （`packages/global/common/file/constants.ts:7`），并被
  `packages/service/common/s3/utils/uploadConstraints.ts:28`（`datasetAllowedExtensions`）与
  `projects/app/src/pages/api/core/dataset/collection/create/localFile.ts:24` 实际使用。
  另有独立"图片数据集"白名单 `datasetImageCollectionFileType = .jpg,.jpeg,.png`。
- **但 FastGPT 能"看懂"视频**：`packages/service/core/ai/llm/utils.ts` 有
  `createVideoContentPart(url) => {type:'video_url', video_url:{url}}`，模型能力声明在同文件
  207-208 行（`{type:'video', fileTypes: videoFileType}`）；`videoFileType = '.mp4,.mov,.avi,.mpeg,.webm'`。
  这些常量只用于**聊天附件**与模型能力检测，不进入 dataset 链路。
- **FastGPT 自带 ASR**：`packages/service/core/ai/audio/transcriptions.ts::aiTranscriptions`
  以 multipart 上传 file 流到 OpenAI 兼容 `/audio/transcriptions`；
  `projects/app/src/pages/api/v1/audio/transcriptions.ts` 是对外接口；默认模型由
  `getDefaultSTTModel()` 决定（需管理员配置 STT 模型）。注意它接收 **fileStream**，需要真实字节。
- **工作流只能读不能写**：`packages/global/core/workflow/node/constant.ts` 只有
  `datasetSearchNode`，没有 dataset 写入节点。→ FastGPT 无法用可视化工作流做"总结后入库"。
- 结论：**FastGPT 零件齐（视频理解 + ASR + 文本 collection 写入 API），但缺"读视频→总结→写库"
  这段编排**；且知识库不能直接上传视频文件。外部对比文章结论一致（FastGPT 视频场景需较多二次开发）。

**RAGFlow 才是真正"现成"的方案**
- Parser 原生支持 Video: MP4/AVI/MKV、Audio: MP3/WAV，另支持 PDF/Image/Email/Text/Word/PPT/Spreadsheet，
  共 8 类 23 种格式。配置 VLM 后上传视频 → 调模型综合解析 → **直接输出 text 成一个 chunk 入库**。
- 参考实现极短，`rag/llm/cv_model.py::QWenCV._process_video`：把视频写临时文件 →
  `messages=[{"role":"user","content":[{"video":f"file://{tmp}","fps":2},{"text":"Please summarize this video in proper sentences."}]}]`
  → `dashscope.MultiModalConversation.call(...)` → 取 `output.choices[0].message.content[0].text` 作为 summary。
  **`fps: 2`（抽帧率）是控制成本的关键旋钮**，正好对应"不必掌握每个细节"。
- 同文件还有 `HunyuanCV`（注意其 `init` 未拼接 self、疑似上游 bug），base_url
  `https://api.hunyuan.cloud.tencent.com/v1` —— 腾讯企业环境可用混元替代 Qwen-VL。
- 视频理解模型示例：qwen3-vl-plus。RAGFlow 也支持"文搜视频片段"，检索结果可溯源到时间戳。

**给 NewsAgent 的三条路**
1. 换/并列一个原生多模态知识库（RAGFlow）承接视频，FastGPT 继续承接图文。
2. 在 FastGPT 上自建薄编排：内容中心视频 URL → 支持 video_url 的多模态模型总结 → 写文本 collection。
   约百行代码，可复用 crawler 的 `create_news_collection`。
3. 直接抄 RAGFlow 那 20 行做 ASR/VLM 总结，产出文本后再走本项目既有的
   `VideoContentTextualizer → KnowledgeBaseWriter` 设计（与本文件上一节结论衔接）。

## ASR 通道定为「腾讯云录音文件识别 CreateRecTask」并修正 4 处事实性错误

用户明确表态："我的建议是用这个东西（CreateRecTask），我如果在腾讯内部的话应该也会用这个"。
本轮据此**逐条核对官方文档**，发现上一轮实现有 4 处与官方不符 —— 其中 1 处是静默的数值错误。
仍为**纯新增/自建文件修改**，未触碰任何既有业务文件。

### 修正的事实性错误（都有官方出处）

1. **`AudioDuration` 单位错**：官方数据结构页明确 `TaskInfo.AudioDuration` 是 **Float、单位「秒」**
   （示例值 1.2 / 2.38）。原实现按毫秒 `/=1000`，会把所有时长缩小一千倍，且**不报错只静默失真**。
   ⚠️ **更值得记住的是**：原测试里我自己编了 `AudioDuration: 19970` 并断言 `19.97`，
   等于"用错误 mock 验证了错误实现"，测试全绿也没发现。→ 用真实形态的数据（19.97）重写。
2. **签名 host 与实际 endpoint 不一致**：`build_tc3_authorization` 硬编码 `host=asr.tencentcloudapi.com`，
   但请求发到 `credentials.endpoint`。换内网域名必然签名失败。→ 新增 `host_of(endpoint)`，装配期即校验。
3. **引擎枚举大小写 + ResTextFormat 兼容性**：官方 `16k_zh-TW` / `16k_zh-PY` 大小写敏感；
   `16k_ja`/`16k_ko`/`16k_multi_lang` 等**只支持 `ResTextFormat=0`**，原实现一律传 3 会直接报错。
4. **`SignedHeaders` 语义**：官方手写示例只签 `content-type;host`，即 **`X-TC-Action` 不参与签名**
   （由 header 承载）。原测试断言"不同 action 产生不同签名"是我自己发明的，已改为
   "payload 敏感 + host 敏感 + action 不敏感"。

### 新增能力（对齐"腾讯内部会这么用"）

- **提交/查询分离**（最重要的架构判断）：`CreateRecTask` 是长时异步任务（1h 音频 1–3 分钟，
  最长 3h）。在单次 RPC 里轮询到完成 → 调用方超时重试会**重复提交、重复计费**。
  新增 `submit_transcription_task()` → TaskId、`describe_transcription_task()` → `AsrTaskSnapshot`；
  `invoke_audio_transcription()` 降级为"便捷入口（联调/短视频）"。
- **可插拔鉴权** `AsrRequestSigner`：`Tc3RequestSigner`（公网密钥）/ `StaticHeaderSigner`
  （内网网关注入头）/ `NoAuthSigner`（内网免签）。对应 `VIDEO_ASR_AUTH_MODE=tc3|gateway|none`。
- **入参 fail-fast**：热词校验（≤30 字符、≤128 个、禁 `|`/`,`）、URL 扩展名白名单
  （无后缀的内网地址放行，不误杀）、时长 ≤5h。
- **`CallbackUrl`** 参数透传（可省轮询）；轮询退避（`poll_backoff`）；`InternalError` → 可重试 Unavailable；
  `TaskId` 兼容字符串与 uint64；`ResultDetail` 用 `FinalSentence ?? SliceSentence`。

### 三个关键决策（后续改动请遵守）

1. **身份头只在开发代理注入，绝不进 `src/`**。本地没有企业网关、后端又强制要求身份头，
   于是 `vite.config.ts` 读 `VITE_DEV_TENANT_ID` / `VITE_DEV_USER_ID` /
   `VITE_DEV_DATA_LOOP_ROLES` / `VITE_DEV_GATEWAY_TOKEN`，在 `server.proxy` 的 `headers` 里补。
   "前端代码永不设置身份头"这条生产不变式仍然成立（生产由真实网关注入）。
2. **同一份代理也挂到 `preview.proxy`**，这样生产构建产物能直接对着真实后端验证，
   不必依赖 dev server（也更接近网关行为）。
3. **`http.ts` 收紧为"预期 JSON 就必须是 JSON"**：网关登录页或反向代理 SPA 兜底会以 200
   返回 HTML，不拦住的话调用方会把字符串当对象用，报出难以定位的运行时错误。
