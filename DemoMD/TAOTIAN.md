电商关键信息提取场景 Auto Research 实践：打通 Data Loop 与 Model Loop，让模型真正「自进化」

本文分享淘天集团商品价格力&营销算法团队在电商场景的多模态关键信息提取任务（KIE）上，搭建 Auto Research 自进化系统的实践经验。模型迭代的瓶颈，很少真的出在算法上。当错例分析、方案调整、训练提交、指标对比全靠人推着走的时候，链路上稀缺的从来不是想法，而是把想法验证完所需要的那几十个小时。我们的做法是把这条链路本身交给Agent来做：通过双Loop打通、Harness 约束设计、以及跨天 Memory 架构设计的方式，让Agent每天自己跑完一整轮实验——从标注回流、错例归因，到生成改进方案、提交训练、评测对比，让人的定位从‘执行者’变更为‘决策者’。一、为什么需要 Auto Research1.1 传统模型迭代的痛点多模态场景，大多数算法团队的模型迭代流程是这样的：线上跑一段时间 → 收集 bad case → 人工分析 → 调整数据/模型 → 重新训练 → 评估 → 上线。这个周期通常是月级别的。我们在实际业务中遇到了两个核心问题： 数据流转摩擦大。 质检、标注、数据回流、训练、评估、上线，每个环节之间都存在大量人工搬运和手动操作。质检结果在群里反馈，运营捞数据筛选问题，算法再从日志表里取数据复现 —— 整条链路冗余且低效。模型迭代速度跟不上线上变化。 业务场景中存在大量 corner case 且不断变化，而模型训练、测试、发版流程较长，难以做到天级别更新。大促等关键时期只能靠大量人力在链路上堆二次校验策略来兜底。618 期间，上述问题被进一步放大：仅仅是电商关键信息提取任务上，算法侧大促周期便累计承接了15个需求优化 case，并在链路中陆续加上了近20个在线生效的校验与交叉验证仲裁策略。这些策略确实能临时兜住 corner case，但代价并不小——一方面每加一条策略都要付出可观的开发与维护成本，另一方面策略里额外引入的模型和随之上涨的 RT，都会在扩量时成为绊脚石。更关键的是，算法同学大量的精力被消耗在这些琐碎 case 的修复上，难以真正投入到业务问题本身的理解、以及把算法能力拓展到更多场景的赋能中去——用"堆策略"换短期的效果稳定，这条路并不可持续。1.2 Auto Research 的目标我们希望实现两件事：数据链路自动流转：质检 → 标注 → 回流训练集，全链路自动化，天级闭环。模型能力天级自进化：基于每日回流数据，通过 Agent 自动完成错误归因、Prompt/Reward 优化、模型训练、效果评估，人工只做最终审核。 
最终效果：从月级人工迭代 → 天级自动化迭代，算法同学从「执行者」变成「审核者」。二、双 Loop 架构总览Auto Research 的核心架构由两个 Loop 组成：Data Loop 负责数据的自动闭环，Model Iteration Loop 负责模型的自动迭代。两者通过共享的数据管道串联，形成完整的自进化引擎。Auto Research双Loop架构三、Data Loop：让数据自己流回来Data Loop 解决的核心问题是：如何让线上产生的 bad case 以最低摩擦变成可用的训练数据。3.1 数据质检（ODPS->质检平台）我们将线上埋点日志接入小时级调度，自动从 ODPS 拉取算法解析结果，并通过应用AI开发工具，搭建了完整的数据回流-质检-标注平台，一键生成质检任务。这一步的关键设计是：质检任务自动关联算法解析的原始结果，质检人员只需判断「对/错」，不需要理解算法内部逻辑。新建质检任务质检流程3.2 数据标注（质检驱动标注）质检结果为「错误」的数据以及策略触发的高不置信数据自动生成标注任务。标注人员在质检完成后直接进行修正标注，产出的标注结果就是高质量的训练数据。这里的关键点是质检和标注在同一平台上无缝衔接，避免了数据在多个系统间的人工搬运。数据标注界面3.3 数据回流（标注平台 → ODPS）标注完成后，通过自动化脚本从标注平台数据库拉取标注结果，上传到 ODPS 的训练数据分区。这一步实现了天级数据自动化回流，Model Loop 第二天就能用到最新的标注数据。Data Loop 的本质： 把原来需要人工串联的「日志 → 质检 → 标注 → 训练集」这条路径自动化。产出的数据是 Model Loop 的燃料。四、Model Iteration Loop：让模型自己跑起来有了 Data Loop 提供的每日新鲜数据，Model Iteration Loop 作为「发动机」驱动模型的自动迭代。4.1 错误归因Agent 自动对比标注结果与算法解析结果，对每个错误 case 进行归因。归因不是简单的「对/错」统计，而是分析错误的类型和原因：是模型能力不足？是 Prompt 描述不清晰？是 Reward 设计有偏差？还是出现了全新的 corner case？归因结果会产出两类输出：一是错误分类报告（供后续 Prompt/Reward 优化参考），二是结构化的归因记录（沉淀到 Memory 中，供跨天分析使用）。4.2 Prompt / Reward 自进化基于归因结果，Agent 自动生成 Prompt 和 Reward 函数的优化建议。这里有一个关键设计原则：Prompt 修改必须经过人工审核才能生效。Agent 只生成建议和 diff，人工决定是否采纳。Prompt/Reward进化建议这个设计是基于一个实际观察：Prompt 的改动可能对多个场景产生连锁影响，Agent 目前还无法可靠地评估全局影响，所以人工审核是必要的护栏。而 Reward 的调整（如权重微调）风险较低，可以设置为自动生效。4.3 模型自动训练数据回流后，Agent 自动完成以下操作：对数据进行训练/测试集划分，与历史数据 merge，形成最新分区新建训练脚本，自动修改数据分区、job_name、存储地址、总迭代次数等参数提交训练任务 对于 Prompt 不变的数据增量训练，默认自动启动；涉及 Prompt 修改的版本，需要人工确认后再提交。这里体现了自主权边界的分级设计（详见 Harness 章节）。4.4 效果评估（轮询机制）训练任务提交后，启动一个定时轮询任务，每隔一小时检查训练输出的 checkpoint 是否生成。一旦检测到新 checkpoint：自动执行新版模型和上一版模型的推理脚本产出测试集精度对比报告对新版模型的错误 case 进行归因分析与历史基线进行对比（双基准对比：线上基线 + 上一实验基线）归因分析轮询任务在报告产出后自动销毁，避免资源浪费。4.5 人工复核上线最终，Agent 产出完整的评估报告，包含：精度对比、bad case 分析、错误归因、Prompt/Reward 修改记录。算法同学基于这些信息决定是否将模型更新上线。五、Harness 设计：让 Loop 跑得稳Loop 流程看起来顺畅，但搭建过程中涉及了大量 Harness（约束与护栏）设计。大部分 Harness 是在交互和试错中由 Agent 自主生成的，但在完全成型之前，每个单点都需要反复确认和 review。Harness 是 Auto Research 系统稳定运行的基石。我们将其分为七类：Harness设计跨天状态管理。 用一份跨天状态台账作为 Single Source of Truth，记录当前线上模型版本、历史 N 天各场景评测精度、持续性错误榜、Prompt/Reward 建议台账，以及每轮实验的上线决策。Auto Research 是跨天的长程任务，每天从零开始归因就无法积累经验——Agent 需要知道哪些错误是新出现的、哪些持续未解决、上次改的 Prompt 效果如何。台账采用原子写入并保留 30 天历史，确保可追溯、可回滚。调度与运行方式。 严格使用平台级定时任务（cron），禁止 nohup、launchd 等临时方案，并在任务 message 中写入完整流程引导，确保 Agent 每次触发都能正确加载 SKILL.md。checkpoint 轮询与评测轮询属于临时任务，产出报告后自动删除自己，避免僵尸任务堆积；同时用 flag 文件做幂等保护，已完成的实验不会被重复提交推理。提交类操作防护。 这是从实际教训中总结出的最重要的一条： 有副作用的命令（提交训练、发送消息等），失败后最多只重试一次。若重试仍失败，改用只读方式排查根因，绝不用不同变体反复重跑。我们曾因为没有限制重试次数，导致同一个 SFT 训练任务被提交了 3 次。从此立下硬规则：提交类操作最多 1 次重试，之后必须转入诊断模式。流程串行与失败策略。 四个阶段严格串行，但失败策略分级：标注数据同步失败属硬阻塞，整条 pipeline 终止；错误归因与跨天状态更新失败可降级继续，允许跳过归因走默认配置；训练数据准备失败阻塞下游，不提交训练；训练提交后转为异步，由轮询任务接管。分级的意义在于——数据层面的错误绝不能绕过（垃圾进垃圾出），分析层面的错误则不该卡住整个流程。自主权边界。 Agent 的定位是「分析者 + 执行者」，而不是「决策者」。数据同步、训练/测试集划分、训练提交、效果评测完全自动；Prompt 修改与模型上线需人工确认；自动修改线上配置、自动部署模型绝对禁止。发布环节还有一层安全机制：20 小时超时默认不发布——人工未响应时系统按"不发布"处理，而不是反过来。环境与技术约束。 训练必须运行在指定环境（框架与依赖版本锁定）；凭证与连接配置统一收口，不散落在各个脚本里；子进程依赖 PATH 而非硬编码绝对路径；save_steps / max_steps 按实际数据量动态计算，不允许写死。文件安全。 用户文件永不永久删除，只移入回收站；修改前自动备份原文件；状态台账原子写入。六、Memory 架构：让 Agent 有「长期记忆」Auto Research 是一个长程且信息不断膨胀的任务。每天的归因结果、实验精度、Prompt 变更记录都在累积。如果没有一个好的知识存储机制，Agent 每天都会「失忆」，从零开始分析。我们设计了四层 Memory 架构：6.1 四层存储各司其职Memory架构Layer 1 — Cron Message（索引）： 定时任务的 message 字段中包含精炼的流程概要。它的作用不是让 Agent 直接执行，而是引导 Agent 去加载 SKILL.md 获取完整的「使用说明书」。类似于一个入口指针。Layer 2 — SKILL.md（操作手册）： 包含 Pipeline 的完整执行步骤、每步的具体命令、约束条件、失败处理方式。这是 Agent 每次执行时的核心参考。内容相对稳定，只在流程调整时更新。Layer 3 — Logs（知识库）： 这是信息量最大的一层，包含：每天各场景的评测精度（overall_acc + 分场景 acc）持续性错误榜（跨天累计哪类错误反复出现）历史建议台账（每条建议的提出日期、是否被人工采纳、采纳后精度变化）每轮实验的上线决策结果这些日志让 Agent 在归因时能参考历史：「这个错误昨天也出现过，上次建议修改 Prompt 的 XX 部分但未被采纳」「这个场景的精度已经连续三天下降，可能需要关注」。Layer 4 — MEMORY.md（经验层）： Agent 在与用户交互过程中，自动提炼和沉淀有价值的信息。例如：某个 ODPS 表的特殊分区规则、某个 UDF 在特定环境下会报错、某个参数调优的经验值等。这些信息来源于实际执行中的试错，是 SKILL.md 无法提前覆盖的。6.2 为什么需要四层而不是一层核心原因是信息的时间尺度和访问模式不同：Cron Message 是每次触发都要读的，所以必须极简SKILL.md 是每次执行都要参考的，所以必须结构化且完整Logs 是按需检索的，Agent 在做归因和对比时才读取相关历史MEMORY.md 是跨会话持续生效的，影响 Agent 对所有任务的决策如果全部塞在一个地方，要么 Cron Message 太长导致 Agent 上下文浪费，要么 Logs 太少导致 Agent 丢失历史信息。分层设计让每层只做自己最擅长的事。6.3 跨天状态：让进化有迹可循跨天状态台账是 Memory 架构中最关键的设计之一。它维护了：最近 N 天的精度趋势（做日环比，自动发现退化）持续性错误榜（跨天累计，识别顽固问题）历史建议台账（追踪每条建议的效果闭环）双基准对比（线上基线 vs 上一实验基线，动态读取而非硬编码）这个文件让 Agent 从「每天从零归因一遍」变成「基于历史先验做增量分析」。这才是 Auto Research 从「自动」升级到「自进化」的关键。七、经验与反思7.1 每条 Harness 都是踩出来的Auto Research 不是搭好框架就能跑起来的。Harness 中的每一条规则，几乎都来自实际执行中踩过的坑：训练任务被重复提交、状态文件被损坏、Prompt 修改导致意外退化…… 在 Harness 构造完全之前，对每个环节是否符合预期需要反复确认和 review。7.2 Agent 的自主权要分级不要让 Agent 做它做不好的决策（如评估 Prompt 全局影响、决定是否上线），但要让 Agent 做它擅长的事（如数据搬运、归因分析、训练提交）。Auto Research 中人工审核不是「可选」，而是「必须」。7.3 Memory 是长程任务的刚需对于单轮任务，Agent 不需要记忆。但对于每天都在跑的 Auto Research Pipeline，没有 Memory 就是每天从零开始。四层 Memory 架构 + 跨天状态文件，让系统能真正积累知识、持续进化。7.4 新时代的 NASAuto Research 的价值不仅限于某个具体模型。它的本质是一种新的 Neural Architecture Search —— 从线上真实 bad case 中自动学习，自动调整模型结构、训练策略和推理 Prompt。不管是多模态大模型还是垂直领域小模型，都可以基于这套双 Loop + Harness + Memory 的架构实现自动化迭代。八、总结实际收益： Auto Research自进化运行一个月，采纳迭代结果5次，模型总体精度从 91.97% 提升到 93.07% ，主力场景提升 +1.90pt，新场景完全依赖Auto Research迭代达到80+水位。该Auto Research方案的四个核心维度总结如下：Auto Research 的最终目标是：让算法同学从「每天修 corner case 的执行者」变成「审核 Agent 产出的决策者」，将精力释放到真正需要创造力的业务和技术探索中。
