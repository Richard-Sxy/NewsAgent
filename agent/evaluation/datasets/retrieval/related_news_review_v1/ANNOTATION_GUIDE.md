# 如何审核这份材料

本包是**预审与试标材料**，不是测试成绩。16 个源新闻任务各有 16 个候选，共 256 对、249 篇不同的候选新闻。候选来自旧源向量、词面、主题与随机采样；当前尚未执行新 A/B 检索，也没有任何默认正确答案。

## 第一步：确认任务，先不做 256 对全量标注

打开 [只读新闻预览](annotation-preview.html)。先确认哪些源新闻值得运营继续追踪，并在 `queries.review.jsonl` 填：

1. `review_decision`：`keep` 或 `drop`。
2. `review_notes`：保留的业务用途，或不适合作为任务的原因。
3. `event_group_id`：同一事件/主线及更正链使用同组名。两个任务即使标题不同，也可能不独立。

当前输入沿用真实业务格式“源新闻标题＋摘要”。不需要另外写自由问题，也不要把候选答案塞进摘要。`split`、`expected_empty`、`status` 暂不修改；分组、候选覆盖与人工判断完善后另行冻结。

先选少量保留任务试标，确认下述等级能表达你的业务需求，再做剩余任务。旧 16 题建议用作开发材料；正式 test 需要未参与调参的事件组。

## 第二步：独立填写相关性判断

评审 A 填 `judgments-reviewer-a.jsonl`，评审 B 填 `judgments-reviewer-b.jsonl`。两人先各自完成，不看对方的分数与理由。用 `pair_id` 对照预览中的源新闻和候选正文，不能只按标题判断。网页是只读材料，真正保存的标签应填入 JSONL。

| 字段 | 填法 |
| --- | --- |
| `reviewer_id` | 自己固定使用的真实评审标识，可用不含敏感信息的代号 |
| `grade` | 经确认的 0、1、2、3 整数；尚未判断保留 `null` |
| `reason` | 简短说明同事件、背景联系或混淆点，最好指出正文依据 |
| `judgment_status` | 本条已完成填 `reviewed`；未完成保持 `pending` |

保持 `pair_id/query_id/news_id` 不变，不删除不相关项。0 分同样是有效人工判断；`null` 不是 0 分。遇到证据无法打开、文本损坏或判断困难，先保持 `null`，用 `reason` 记录原因，等待补证据。

建议业务确认的等级：

| 等级 | 对源新闻的业务价值 |
| --- | --- |
| **3** | 同一事件，直接补充关键事实、进展或更正信息 |
| **2** | 有实质解释价值的背景或关联事实，能帮助理解该事件 |
| **1** | 仅主体或主题相近，没有实质补充；不能因为都提到同一家公司就判高分 |
| **0** | 无关、事件混淆，或无法支撑当前关联用途 |

时间较近不自动加分，较早的关键背景也可能有价值。正文与源新闻矛盾时，判断它是否属于有依据的更正或争议报道，在理由中记录；不要直接把“立场相反”当作无关。转载或近似副本需要注明，之后按预先确定的去重口径处理。

两份表都为空白模板，并不代表已经有两位评审。现有 `score_retrieval_judgments.py` 会检查两位不同评审；分歧还需独立的第三位裁决，之后才合并成 `qrels.jsonl`。若今天只有一位评审，可以先做试标和口径确认，保留真实状态。

## 第三步：再进入正式评测

1. 固定任务、语料、模型与分层参数，在相同输入上运行 A（三级 RRF）和 B（三级 RRF＋业务重排）。
2. 合并实际 A/B Top20 与预先确定的补充检索候选。旧预审池只作起点，不假定它已完整覆盖。
3. 新增候选同样隐藏策略、分数和排名，完成独立盲审及分歧裁决。保留旧记录，新增版本而不覆盖历史。
4. 审核事件组与 split、无答案判断、正文与索引哈希，确保每套方案的 Top5 都已标注。不能把未判候选当负例，也不能按召回失败删题。
5. 用冻结的 `queries.jsonl/qrels.jsonl/predictions.jsonl` 执行 `--ks 5`。本包的两份原始评审表不能直接传给评分器。

计时单独执行，保持 Embedding、三层检索、过滤和业务重排的边界一致。简历的 N 是正式留出查询数；256 是候选判断对数，两者不能混用。
