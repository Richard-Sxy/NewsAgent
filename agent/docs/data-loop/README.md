## 核心判断

运营策略是一条有边界的决策规则：**在什么新闻背景和证据状态下，对什么人群，在什么时间，用什么渠道与表达，执行推送、延后、合并或不推；如何判断结果，以及何时失效。** 高热度、高点击率、一次批准都不能单独证明它是可推广策略。

应分别积累事实、决策、结果与经验：

```text
Observation：当时的新闻/事件/指标/证据与候选建议快照
→ Decision：运营动作、结构化理由、修改差异、操作者与时间
→ Outcome：未执行/模拟执行/真实执行事实及可用的聚合效果
→ StrategyCandidate：适用条件、反例、证据、评测与推广范围
→ 人工审核和版本激活
→ ApprovedStrategySet：供后续建议选择的不可变策略集
```

## 当前与目标

| 能力 | 当前代码事实 | 本窗口的目标 |
|---|---|---|
| 热点运营决定 | 已支持采纳、驳回、延后、修正；对象是分析建议 | 扩展为针对完整推送建议修订版的审批 |
| 回流 | 驳回/修正原子生成 FeedbackCase；采纳/延后只保存决定 | 完整记录四类决定，区分编辑判断、策略判断与模型错误 |
| 候选推送 | PushPlan Schema、生成器、确定性 Validator 与单测存在 | 接持久化、审批 UI 与专属有界 Workflow |
| DataLoop | 已有标签二审、三层集、回放、Gate、48 小时审批和配置激活/回滚 | 复用治理能力，补策略领域与迟到反馈消费 |
| 长期策略 | 没有团队策略注册表；个人 Memory 不能替代 | 租户/运营团队作用域、人工审核、策略集版本与撤销 |
| 真实投递 | 推送人群/投递 Port 和专属 Workflow 未接通 | 首阶段仅做模拟/shadow；真实触达按独立生产授权推进 |

四种权限不能互相替代：单条建议审批、案例标签二审、通用策略审核、生产配置发布审批。现有 DataLoop 的 `approve` 会推动 Workflow 记录决定并激活候选 Bundle；它不是单条新闻的发送许可。

## 存储与安全边界

PostgreSQL 保存事实与审批账本，S3/MinIO 保存带哈希的不可变快照，Temporal History 保存控制流与等待，Redis/SSE 只提供投影。Markdown 是研究、评审和导出载体；本次没有新增 Markdown 自动加载器，也不能让模型生成的 Markdown 自行变成生产规则。

指标、阈值、匹配、频控与门禁由 Python/SQL 执行。模型可以解释、提出策略候选，不能批准、改变租户范围、选择未批准版本或跳过门禁。模型输出、新闻正文、案例理由和检索策略文本都是不可信输入。
