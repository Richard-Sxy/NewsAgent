## Feed 是什么

Feed 是用户看到的一串内容条目或卡片，常通过滑动、刷新、翻页不断获取下一批。
它描述的是**内容列表的组织与交付形态**，不自动等于“个性化推荐榜”。

- 推荐 Feed 可以按访问情境、兴趣、内容质量和时效选择并排序。
- 关注 Feed 可以以关注的作者或媒体为供给来源。
- 编辑组织的 Feed 可以以重要性和编辑选择为主。
- 频道 Feed 可以先按主题限定范围，再采用推荐或编辑排序。

腾讯新闻自身的公开技术案例也有清晰的分层：provider 获取不同来源的列表，loader 加载文章数据，
packer 按列表顺序打包卡片；内容提供方包括推荐、配置、热点榜，基础打包复用 feed 服务。
这是 2025-01 发布、描述 2023 年起重构的历史工程案例，不代表其所有当前场景都共用相同流程。
[腾讯新闻插件接入层重构实践](https://cloud.tencent.com/developer/article/2483974)

## 热点榜与 Feed 的区别

| 维度 | 热点榜 | 推荐 Feed |
| --- | --- | --- |
| 核心问题 | 某个范围内，此时哪些内容更热门/更受关注 | 这次访问，哪些内容适合先展示 |
| 排名范围 | 全站、地域、频道或指定群体；也可以有个性化榜 | 具体访问情境和推荐目标 |
| 输入 | 行为聚合、时效、质量与明确版本规则 | 候选内容、兴趣/关注、情境、质量及实时信号 |
| 结果 | 有名称、范围、窗口和版本的榜单快照 | 一次交付的有序内容列表与卡片 |
| 位置 | 原榜 rank / source_position | Feed position；不等同于原榜名次 |
| 与 SQL 的关系 | 有界聚合、候选与规则计算适合读数仓 | 通常需要在线推荐服务，数仓提供统计/特征输入 |

“全站热门”不必对每个人排第一；“只在某小众领域相关”的内容也可以进入合适用户的推荐 Feed。
榜单可以给 Feed 提供一路候选，Feed 还可以使用关注、新内容、编辑供给等其他来源。
在 Feed 中重新排序的文章不能反过来覆盖它在来源原榜上的名次。若是直接展示原榜卡片，应保留
提供方的名次和位置语义。

常见推荐系统是“候选生成 → 打分排序 → 重排”；粗排/精排是可以按容量选择的进一步拆分，
不是每个 Feed 必须具备的固定组件。[Google 推荐系统说明](https://developers.google.com/machine-learning/recommendation/overview/types)

## 二者如何形成反馈闭环

```text
可用的真实内容库
 ├→ 数仓合格聚合 → 热点候选/项目热度榜 ──┐
 └→ 兴趣、关注、新内容、编辑供给 ─────────┤
                                        ↓
                            推荐候选生成 → 排序/重排
                                        ↓
                              Feed卡片交付给用户
                                        ↓
                      有效曝光 → 点击 → 阅读/互动/负反馈
                                        ↓
                            企业端去重、归因与聚合
                                        ↓
                         数仓快照 / 内容与策略统计
                         ├→ 下一版榜单
                         └→ 推荐特征与效果评估
```

该图是通用逻辑及 NewsAgent 设计建议。线上推荐不应被简化成“每次刷新都 SQL 查同一份 Top20”。
一条新闻获得更多分发位置，会有更多曝光机会，也可能获得更多点击，从而继续推动热度。
因此点击上升不自动证明内容本身更受欢迎，CTR 也不能自动消除位置、人群选择与策略差异。
位置偏置对点击反馈的影响已有研究，具体 Feed 场景仍需自己的归因与实验验收。
[Joachims 等的原始研究](https://arxiv.org/abs/1608.04468)

必须区分“服务端返回卡片”“客户端渲染”“用户有效看到”。有效曝光的可视范围、停留条件和
点击归因窗口应在业务合同中版本化，不编造腾讯新闻内部的具体阈值。

## 对 NewsAgent 的榜单设计建议

下表都是**拟议模拟设计**，不是腾讯新闻内部既有清单，也不是本次已经上线的榜单。

| 模拟榜单 | 回答什么 | 当前数据与约束 |
| --- | --- | --- |
| 综合热点榜 | 哪些新闻/事件正在受关注 | 当前 Python 热度规则在 v6；v8 待适配。事件榜另需新闻—事件映射 |
| 频道榜 | 科技、财经、体育等范围内哪些内容热门 | 栏目可作筛选维度；v8栏目是演示标签 |
| 上升榜 | 哪些内容比同口径历史更快升温 | 保留样本数、NULL与零基线，设置批准的样本门槛 |
| 深度阅读榜 | 哪些内容带来更深入的阅读 | 使用时长/PV、点击归因有效阅读率等；完读率目前未采集 |
| 互动榜 | 哪些内容得到更多讨论和传播信号 | 点赞/评论/分享/收藏为次数，不能冒充互动人数 |
| 运营巡查列表 | 哪些内容或策略值得检查 | 负反馈、质量门禁、修订变化等；与面向用户的推荐榜分开 |

推荐的 `ranking_kind` 可以区分 `click_volume / detail_pv / detail_uv / interaction_volume /
ctr / rising / project_hot / editorial_original`。`scope` 再保存频道/地域/群体/时间窗，
`source_kind` 区分模拟指标榜、项目计算榜、编辑原榜和企业原榜。Feed 场景单独保存，不塞进榜单枚举。
算法规则、Prompt、Bundle 与生产发布仍沿用版本化与人工批准边界。

如果原榜按事件而当前数仓按文章，必须建立独立事件标识与文章成员关系；一个事件里的多篇文章
不能当成多个独立事件，也不能直接累加文章 UV 作为事件去重人数。当前 v8 还没有这一完整事件模型。

## 当前 v8 已有什么，尚缺什么

当前 `dim_channel` 的 recommend、hot_board 只表示模拟消费入口；已有五分钟、渠道小时、新闻小时、
单新闻每日、基线与资格视图。固定 SQL 能按点击、CTR、访问PV/UV和互动选候选。
这些入口值不证明推荐模型、在线Feed、原始热榜或 A/B 实验服务已经运行。

v8 仍未接入现有 Agent；没有 Feed 策略、实验桶、展示位置维度，也没有原榜快照表。
单新闻小时/日 UV 不能跨渠道、位置组、实验桶、新闻或日期直接相加。

下一版建议只增加必要的**聚合数据**，不在本地保存企业 user/device/session 明细：

- `dim_feed_policy`：租户、场景、策略/模型版本、实验与桶、曝光定义版本、归因定义版本。
- `feed_metric_hourly`：租户、真实news_id、小时、入口、策略、实验桶、位置组、修订；
  保存交付条目、渲染曝光、有效曝光、归因点击/详情PV、有效阅读、时长、负反馈和范围明确的UV。
- 榜单来源快照：榜单ID、版本、范围、窗口、原始名次/位置/分数、提供方和内容资格。

去重和点击归因在企业端完成，本地只接收聚合；直接访问与 Feed 归因访问分开。
策略效果应结合批准的随机实验或经验证的评估方法，不能仅按不同桶 CTR 的大小宣称因果提升。
这些是设计建议，本次没有修改冻结 v8 Schema、生成更多行为数据或部署在线推荐服务。

## 撤稿为什么要同时管 Feed、榜单与向量库

同一内容资格机制应覆盖所有出口：可信状态事件 → 状态/tombstone → 快速 denylist →
Feed与缓存、热点展示、检索及模型证据提交复核 → 异步版本化物理清理。
物理删除失败不能解除屏蔽；历史聚合统计按审计/留存规则处理，不能与“当前可展示”混为一谈。
v8目前只有资格视图与隔离租户的 pending 清理演练；真实通知、Feed缓存屏蔽、denylist执行器与向量删除待接入。
